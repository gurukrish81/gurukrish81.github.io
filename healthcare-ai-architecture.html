Full-Stack Architecture — Layer by Layer
Healthcare AI — Data Flow Architecture READ TOP TO BOTTOM → DATA INGESTION TO PATIENT OUTPUT
L1
Data Ingestion & Source Systems
HIPAA §164.312(a) OWASP LLM06

EHR / EMR Integration

HL7 FHIR R4 API connection to Epic, Cerner, or Meditech. Patient records, encounter history, problem lists.

▪ HIPAA: Access control + audit log required for all PHI reads
▪ OWASP LLM06: Sensitive data exposure — PHI must be de-identified or encrypted before LLM ingestion

Clinical Dictation / Audio

Physician voice input via microphone or dictation device. Transcribed via speech-to-text before LLM processing.

▪ HIPAA: Audio recordings containing PHI require same access controls as text records

Patient Intake Forms

Structured symptom questionnaires, chief complaint capture, demographic data from patient portal or kiosk.

▪ OWASP LLM01: Prompt injection — patient-supplied text must be sanitized before passing to LLM

Lab / Imaging Results

HL7 v2 or FHIR DiagnosticReport resources. Lab values, radiology reports, pathology results.

▪ HIPAA: PHI classification — all lab values are protected health information
↓
L2
PHI Handling & Preprocessing
HIPAA §164.514 De-ID OWASP LLM06 Critical Control

PII/PHI Detection

Microsoft Presidio or AWS Comprehend Medical scans all inbound text for 18 HIPAA identifiers (name, DOB, MRN, SSN, address, etc.).

▪ HIPAA §164.514(b): Must remove all 18 identifiers for safe harbor de-identification
▪ OWASP LLM06: PHI leakage prevention — block identifiers from reaching LLM context window

De-Identification / Tokenization

Replace PHI with reversible tokens (PATIENT_001, DOB_REDACTED) for LLM processing. Token vault maintains mapping for re-identification on output.

▪ HIPAA: De-identified data no longer subject to PHI rules — enables safe LLM processing

Input Validation & Sanitization

Strip control characters, normalize encoding, enforce max token limits. Validate that input structure matches expected schema.

▪ OWASP LLM01: Prompt injection defense — sanitize all patient-supplied and third-party content

Encryption in Transit

TLS 1.3 minimum for all data movement. PHI never traverses network unencrypted. Key management via AWS KMS or Azure Key Vault.

▪ HIPAA §164.312(e)(2)(ii): Encryption required for ePHI in transit
↓
L3
Embedding & Vector Store (RAG Layer)
OWASP LLM10 HIPAA Access Control

Clinical Knowledge Base

De-identified clinical guidelines, drug interactions, ICD-10 coding rules, formularies. Embedded and stored in vector DB.

▪ HIPAA: Clinical KB must not contain patient-specific data — population-level only

Vector Store (Pinecone / Weaviate)

Semantic search index for relevant clinical context retrieval. Patient history embeddings stored with access controls by MRN scope.

▪ OWASP LLM10: Model theft/data exfiltration — vector store must be access-controlled, not publicly queryable

Context Assembly

Retrieves top-k relevant chunks from vector store. Combines patient context (tokenized) + clinical guidelines into LLM prompt.

▪ OWASP LLM04: Data poisoning — validate retrieved chunks for integrity; malicious injection into KB must be prevented

Embedding Model

text-embedding-3-large (OpenAI) or equivalent clinical-tuned model. Separate from generation LLM. Version pinned.

↓
L4
LLM Inference Engine
OWASP LLM01 · LLM02 CRITICAL — Full Guardrail Suite

System Prompt & Constraints

Hardcoded clinical persona and constraints. Explicit prohibitions: no diagnoses, no prescriptions, no treatment recommendations without HITL sign-off.

▪ OWASP LLM01: Jailbreak defense — system prompt includes injection-resistant framing
▪ Scope limitation: system prompt enforces "document and route only" behavior for triage use case

LLM (Claude / GPT-4 / Gemini)

Anthropic Claude or equivalent. Version pinned in production. Temperature: 0.1 for clinical documentation (determinism required). No internet access.

▪ OWASP LLM02: Insecure output handling — all LLM outputs treated as untrusted until post-processing validation

Input Guard (Lakera Guard / Rebuff)

Pre-LLM guardrail layer. Detects prompt injection attempts, jailbreaks, PII leakage in constructed prompt. Blocks before LLM call.

▪ Lakera Guard: Classifies injection attempts in real-time. Blocks >95% of known attack patterns

Output Guard (Post-Processing)

Validates LLM output against schema. Runs PII scan on output. Blocks responses containing diagnosis keywords or prescriptive language without HITL flag.

▪ HIPAA: LLM output must not contain PHI beyond what was tokenized in — re-identification check before delivery
↓
L5
Safety Guardrail Layer
OWASP LLM09 CRITICAL — Required for Patient Safety HIPAA §164.308

Clinical Safety Classifier

Fine-tuned classifier that flags outputs containing: diagnosis statements, drug dosage recommendations, "do not resuscitate" or DNR language, suicide/harm indicators.

▪ OWASP LLM09: Overreliance — system must not allow clinical decisions to be made without clinician review
▪ Any flagged output routes to HITL queue before delivery

Hallucination Detection

Groundedness check: verifies LLM output claims are traceable to retrieved context. Ungrounded assertions flagged for clinician review.

▪ Clinical notes must be grounded in provided patient data — hallucinated clinical details are a patient safety risk

Output Schema Validation

Enforces expected output structure (SOAP note format, triage code, ICD-10 list). Rejects malformed outputs rather than passing them downstream.

▪ OWASP LLM02: Prevents malformed/adversarial output from reaching clinical systems

Audit Logger (Immutable)

Logs: full input, output, model version, confidence scores, guardrail decisions, timestamp, clinician ID (anonymized). Stored in append-only log store (AWS CloudTrail / Azure Monitor).

▪ HIPAA §164.312(b): Audit controls — maintain log of access and activity for all ePHI systems
↓
L6
Human-in-the-Loop (HITL) Checkpoint
CRITICAL Tier — Mandatory HIPAA §164.308(a)(3)

Clinician Review Queue

Flagged outputs held in queue until reviewed and approved by licensed clinician. SLA: <4 hours for non-emergency, <15 minutes for triage routing.

▪ HIPAA: Clinician sign-off creates accountability chain for PHI-based decisions

Review Interface

Clinician sees: AI-generated draft, source data used, confidence score, flagged concerns. One-click approve, edit, or reject with reason code.

Approval Audit Trail

Every approval logged: clinician ID, timestamp, action taken (approve/edit/reject), reason code, final output delivered.

▪ HIPAA: Creates non-repudiable record of clinical decision accountability

Feedback Loop to Model

Rejections and edits tagged for model evaluation. Monthly review by clinical informatics team. Significant drift triggers model re-evaluation gate.

↓
L7
Output Routing & Delivery
HIPAA §164.312(e) OWASP LLM08

Re-Identification (Clinical Notes)

Reverse tokenization: replace patient tokens back with actual identifiers before writing to EHR. Token vault lookup with access control.

▪ HIPAA: Re-identified output is PHI — must be written to secured clinical system only, not returned to requestor without access control

EHR Write-Back

FHIR DocumentReference write to EHR. Clinician approval required for write to become permanent. Versioned — original AI draft preserved alongside clinician-edited final.

▪ OWASP LLM08: Excessive agency — AI write to EHR must require explicit clinician approval at each instance

Triage Routing Decision

Approved triage output triggers routing: ED admission queue, urgent care referral, telehealth queue, or primary care scheduling. Decision logged with clinician ID.

Patient-Facing Communication

Patient receives: triage category (non-clinical language), estimated wait, next steps. AI-generated — not containing diagnosis. Reviewed by triage nurse before send.

▪ HIPAA §164.312(e): Patient communication via secure messaging only (not plain email)
OWASP LLM Top 10 — Threats Mapped to This Architecture

🔴 OWASP Threats in This Stack

LLM01 Prompt Injection — Patient-supplied text in intake forms and EHR notes can contain injection payloads. Mitigated at L2 (input sanitization) and L4 (Lakera Guard).
LLM02 Insecure Output — LLM outputs treated as untrusted until L5 guardrails validate structure and safety. Clinical system receives only validated outputs.
LLM04 Data Poisoning — Clinical knowledge base could be poisoned with inaccurate guidelines. Mitigated by L3 source validation and clinical informatics curation.
LLM06 Sensitive Data Exposure — PHI must not reach LLM context unprotected. Mitigated by L2 de-identification before any LLM call.
LLM08 Excessive Agency — AI must not write to EHR or route patients without explicit clinician approval. Enforced at L6 (HITL) and L7 (approval-gated write).
LLM09 Overreliance — Clinicians may over-trust AI output without clinical review. Mitigated by L5 classifier, L6 HITL mandate, and training program.
LLM10 Model Theft / Exfiltration — Vector store and fine-tuned models are high-value IP. Mitigated by L3 access controls and network isolation.

🟣 HIPAA Technical Safeguards — Controls in This Stack

§164.312(a) Access Control — Role-based access to EHR integration (L1), vector store (L3), clinician review queue (L6).
§164.312(b) Audit Controls — Immutable audit log at L5 captures all access and decisions. Retained per retention schedule.
§164.312(c) Integrity — Output schema validation at L5 prevents unauthorized alteration. Versioned EHR writes at L7.
§164.312(d) Authentication — Clinician ID required at L6 before any approval action. SSO + MFA enforced for clinical staff.
§164.312(e) Transmission Security — TLS 1.3 at L2 and L7. Patient communications via secure messaging only.
§164.514(b) De-Identification — Safe harbor de-identification at L2 (18 identifier removal) before LLM processing.
§164.308(a) Security Management — Governance framework, workforce training, and access management procedures cover AI staff.
